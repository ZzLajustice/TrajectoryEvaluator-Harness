# 任务 32：`aggregator` 与终端报告

> **所属里程碑**：M8 · **前置任务**：27（用例集加载）、29（`Scheduler`，产出每条 case 的终态） · **代码位置**：`src/harness/orchestration/aggregator.py`、`src/harness/report/terminal.py`

## 1. 总体目标

把 N 条用例 × repeat 次的原始结果压成可比较的数字，并保证压缩过程**不丢失可行动的信息**。

痛点在于：单看「通过率 0.8」这句话无法驱动任何决策。它可能是「80% 的 case 稳定解出」（能力问题已解决）、也可能是「所有 case 都能解出，但每次只有 80% 的概率成功」（稳定性问题）、还可能是「一半 case 稳过，另一半完全无解」（难度分层问题）。这三种情况在同一个数字下完全同形，而修复手段分别是「扩数据」「加确定性」「拆用例」。

因此本任务的核心不是算数，而是**指标语义的分列**：`pass_rate` / `pass@k` / `flaky_rate` 三个指标各回答一个不同的问题，绝不合并成一个总分；过程分（golden 匹配）与结果分（outcome）也分列。

## 2. 实现流程

1. 定义 `CaseOutcome` 值对象：`case_id` + `statuses: list[RunStatus]` + `golden_score` + `cost_usd` / `turns` / `tool_calls`，并提供 `successes` / `pass_rate` 两个派生属性。
2. `aggregate(outcomes) -> dict` 纯函数，返回普通 dict。
3. 终端渲染（`rich`）：指标表 + status 分布 + **flaky case 单独一节**。

两处顺序与形状的理由：

**先定 `CaseOutcome`，而不是直接吃 `EvalResult`。** 聚合需要的是「每次 repeat 的终态」，而不是评测器结论——把输入形状定死成 `list[RunStatus]`，聚合逻辑就成了纯函数，可以完全离线单测（不需要跑 agent、不需要 store、不需要 provider）。测试里 `_o("a", RunStatus.OK, RunStatus.NO_FINISH)` 这种一行构造，正是输入形状定得好带来的收益。

**空输入先早返回，且返回全 key 的 dict。** `n == 0` 时返回 `{"cases": 0, "pass_rate": 0.0, ..., "golden_score_mean": None}`，不是 `{}`。这不是防御性编程的样板，而是让「空 suite」有一个明确的、形状固定的输出——下游 HTML 模板（任务 33）与 diff 脚本（任务 34）不会因为缺 key 崩掉。**下游的健壮性应该来自上游输出形状的确定性，而不是下游的防御性代码。**

## 3. 具体技术实现

### 3.1 三个指标的语义区别

| 指标 | 定义 | 回答的问题 |
|---|---|---|
| `pass_rate` | **所有** repeat 都 `OK` 的 case 占比 | 「稳定通过的能力」 |
| `pass@k` | **至少一次** `OK` 的 case 占比 | 「能力上限 / 可达性」 |
| `flaky_rate` | 通过率落在 `(0, 1)` 区间的 case 占比 | 「不稳定性」 |

举例：3 条用例、每条 repeat 3 次。A 三次全过，B 三次全败，C 三次中过一次 → `pass_rate = 1/3`，`pass@k = 2/3`，`flaky_rate = 1/3`。

**为什么必须分列**：单看 `pass_rate` 掉而 `pass@k` 不掉，含义是「模型能解，但不稳」——修复方向是降温度、减少对上下文的依赖、把不确定的工具调用换成确定性的；两个一起掉才是能力问题。合并成一个平均分，会把这两种完全不同的诊断结论抹成同一个数字，团队接下来只能靠猜。

**注意 `pass@k` 这个词的歧义**：业界常说的 `pass@k`（无偏估计）指「一次生成 k 个样本至少一个正确」。这里的定义是 harness 层面的「k 次 repeat 中至少一次通过」，是**经验值**而非估计量。报告脚注必须写清楚，否则会被质问。

**同名不同层次**：`CaseOutcome.pass_rate` 是 case 内的通过比例，聚合输出的 `pass_rate` 是 case 之间的比例。两者同名但层次不同，写代码时容易读错。

### 3.2 flaky case 要列出，不能只给比率

```python
flaky = [o.case_id for o in outcomes if 0.0 < o.pass_rate < 1.0]
```

比率告诉你「有多少」，列表告诉你「哪些」——只有后者能行动。终端报告因此把 flaky case 单独成节，放在聚合表之外：它是全部输出里唯一需要「逐条看」的信息，塞进表格会被读过去。

### 3.3 过程分与结果分分列

```python
"golden_score_mean": (sum(golden) / len(golden)) if golden else None,
```

- golden 匹配分是**次要判据**（过程分），outcome（隐藏测试通过）永远是主判据。
- 合并成一个总分，会让过程评测的意义被 outcome 淹没——那正是本项目要反对的。
- 没有 golden 时返回 `None` 而不是 `0.0`。`0.0` 表示「过程分是零」（一个真实的坏结果），`None` 表示「这一轮没测过程分」。两者会导致完全不同的行动，混用是数据报告里最常见的错误。

### 3.4 status 分布与成本汇总

`status_distribution` 用 `Counter` 累计每个 `RunStatus.value`。它比比率更有诊断力：`no_finish` 偏多说明 agent 不知道何时停止（改 `finish` 契约或 prompt），`budget_exceeded` 偏多说明任务太难或预算太紧（调 `max_turns` / `max_usd`），`llm_error` 偏多则是 provider 层的问题（任务 16）。

`total_cost_usd` / `total_turns` / `total_tool_calls` 是绝对量，与比率配合才有解释力：`pass_rate` 掉了 5 个点，如果 `total_cost_usd` 涨了一倍，那是「模型变啰嗦了」而不是「模型变笨了」。

### 3.5 终端报告

`rich` 渲染上面这个 dict。关键点只有一条：**flaky case 单独一节**，不与聚合指标混在一起。其余是常规的表格与面板。

## 4. 使用的技术栈简介

| 项 | 版本 | 事实 | 替代与取舍 |
|---|---|---|---|
| `rich` | 用 `>=14.1,<16` | deepeval / ragas / inspect_ai 全都用它 | 必须避开 14.0.0（inspect_ai 特意排除）；`rich` 15 是 2026-04 的新大版本，生态未全跟上（deepeval 仍钉 `rich>=13.6,<15`），故不进 15 |
| `typer` | 0.27.2 | ragas / deepeval 两条评测赛道都选它 | 内置 rich 集成；`click` 是它的底层，只有需要极细粒度控制时才直接写 |
| `dataclasses` / `Counter` | stdlib | — | 聚合层刻意不引入 numpy/pandas：几十个 case 的规模上，`sum` 与 `Counter` 更可读，且零依赖 |

`textual` 明确不做（设计文档 §1.3：静态 HTML 已满足 demo，TUI 是另一条能力线）。终端报告是「本地开发时快速看结果」的通道，不是交付物——交付物是任务 33 的 HTML。

## 5. 工程化思想

**指标分列的本质是不把多维信息投影到一维。** 任何「综合得分」都会让团队优化分数而不是优化系统（Goodhart 定律的工程形态）。可迁移的判据：**当两个数字掉下来会导致完全不同的行动时，它们就不该被加起来**。性能看板的 P50/P99、代码质量的覆盖率/复杂度、可用性的成功率/延迟，都是同一个结构。

**缺失值必须与零值区分。** `golden_score_mean: None` 与 `0.0` 的区别是「没测」与「测出来是零」。用 `0.0` 兜底会让「这轮没跑过程评测」和「过程分全军覆没」长得一样——而报告的全部价值就在于区分它们。这条原则在任务 35 会以另一个形式再出现（单次判定时 consistency 报 `None` 而非 `1.0`）。

**聚合的输出形状要显式且完整。** 空输入也返回全 key，让下游不需要写 `data.get("x", 0)` 这类补丁。上游形状确定 → 下游逻辑简单，这个方向的依赖关系不能反。

**把「需要逐项看的信息」从聚合里拎出来单独呈现。** 比率和列表服务不同的读者：前者给决策者看趋势，后者给工程师看行动项。把它们放进同一个表里，服务的是谁都不满意。

**聚合层应该是纯函数。** 输入是值对象、输出是 dict、没有 I/O——这让「指标语义」这件最容易出错的事可以用几行测试钉死，而不必每次跑一遍真实评测来验证算数。
